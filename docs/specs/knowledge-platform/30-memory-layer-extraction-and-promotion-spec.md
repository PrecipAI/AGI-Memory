## 1. 目标

本规范定义统一长期知识系统中的各层对象边界，明确：

- 短期记忆应存放在哪里。
- 治理证据层应存放什么，以及它与短期记忆的区别。
- `rule / long-term memory / short-term memory / skill / knowledge / evidence / audit` 各自承载什么。
- 新输入默认先落到哪一层。
- 何时升格、何时降级、何时删除。
- 当前系统是否足以支撑目标效果。
- 如果不足，还缺什么，应该如何补强。

本规范的目标不是“先把东西都抽出来”，而是“只把合适的内容抽到合适的层里”。

## 2. 本轮确认结论

以下结论已经由用户确认，后续实现必须严格遵守：

1. `knowledge` 只允许承载外部通用知识，不承载系统内部、项目内部、机器内部、用户偏好类上下文。
2. 系统内、项目内、机器内、用户偏好类内容，只能进入 `rule` 或 `memory`，不得误入 `knowledge`。
3. 新搜索到但尚未完成治理的外部内容，默认只进入短期层，不直接进入长期 `knowledge`。
4. 用户不会逐条指出“哪条对、哪条错”；系统必须自己补齐合理分层标准，并通过测试逐步逼近正确抽取效果。
5. 当信息仍不足以支撑关键设计，或继续靠猜测会造成高返工风险时，必须通过 `interview` 补访谈，而不是继续硬推。
6. 治理层禁止“为了产出而产出”；没有长期价值的内容不得为了填满结果而进入长期层。
7. 需要单独存在一个“治理证据层”，保存对话记录之外、治理时必须读取但日常问答不应直接读取的信息。

## 3. 总原则

所有新输入在分层前，先回答三个问题：

1. 这是外部知识，还是系统内部/个体化上下文。
2. 这是长期稳定，还是当前任务/当前阶段临时有效。
3. 这是可复用规律/约束，还是一次性过程痕迹/证据。

只有先回答这三个问题，后续分层才有意义。

## 4. 分层模型

在本规范下，系统正式拆成五类层：

1. `conversation / execution record layer`
2. `working memory layer`
3. `governance evidence layer`
4. `governance synthesis layer`
5. `long-term governed layers`

其中：
- 会话记录层负责保真记录。
- 工作记忆层负责当前任务上下文装配。
- 治理证据层只为治理服务，不为日常回答直接服务。
- 治理综合层负责分类、合并、抽象、冲突处理。
- 长期层只保留最终克制后的结果。

## 4.0 总体约束

治理层的首要原则不是“有产出”，而是“不要污染长期层”。

必须遵守：
- 没必要的内容，不产出。
- 无法证明具有长期价值的内容，不进入长期层。
- 宁可保留在治理证据层或直接丢弃，也不要把低价值内容写进 `rule / memory / skill / knowledge`。
- 治理结果的价值优先于治理结果的数量。

这条原则高于“每轮都要整理出很多条目”的冲动。

## 4.0.1 Conversation / Execution Record Layer

定义：
- 原始记录层，保存完整对话、commentary、命令、工具调用、MCP 调用、验证结果、文件改动摘要等原始底稿。

作用：
- 保真存档
- 审计
- 回放
- 为治理层提供完整原始材料

它不是短期记忆，也不是长期记忆。

适合进入这一层的内容：
- 用户与 assistant 的完整会话消息
- commentary
- shell 命令与关键输出
- tool call / MCP call
- 文件改动摘要
- 验证动作与验证结果

不适合进入这一层的内容：
- 已抽象后的规则
- 已治理后的长期 knowledge
- 当前任务的结构化工作集

## 4.1 Rule

定义：
- 严格执行的硬约束，只允许 `must` / `must_not`，并且必须是**直接对 agent 自身生效**的行为约束。

适合进入 `rule` 的内容：
- 用户明确给出的长期强约束。
- 治理与审批边界。
- 上下文装配中的强约束。
- 安全、权限、修改边界、流程边界。
- 直接约束 agent 的行为要求，例如“先补访谈再继续”“未经确认不得修改真实 skill”“不要靠猜测补空白”。

进入条件：
- 能直接约束后续 agent 行为。
- 跨会话稳定。
- 不是一次性状态说明。
- 不是普通事实描述。

不该进入 `rule` 的内容：
- 项目路径。
- 某次命令成功。
- 某次接入验证通过。
- 某次测试结果。
- 项目内部的实现方案、分层决策、系统设计边界。
- 应该通过修改项目本身来落实的治理机制。

## 4.2 Long-term Memory

定义：
- 个体化、系统内、长期稳定、需要跨会话记住的事实。

建议子类：
- `user_memory`
- `project_memory`
- `environment_memory`
- `decision_memory`

适合进入 `long-term memory` 的内容：
- 用户长期偏好。
- 项目长期背景与约束事实。
- 机器/环境稳定事实。
- 已确认的设计决策。
- 已验证的失败模式总结。

进入条件：
- 与当前用户、项目、机器、系统强相关。
- 后续高概率重复用到。
- 稳定期足够长。
- 不是当前一次执行中的临时痕迹。

不该进入 `long-term memory` 的内容：
- 新搜到的一篇论文。
- 新打开的一个 GitHub 项目。
- 当前线程临时查到的资料。
- 一次命令输出。
- 一次 MCP 调用记录。

## 4.3 Working Memory Layer

定义：
- 当前任务或当前阶段临时有用、用于上下文装配和当前执行推进的结构化工作记忆。

这一层必须单独存在，不能拿长期 `memory` 顶替，也不能和治理证据层混在一起。

适合进入 `working memory` 的内容：
- 当前任务新发现的外部资料。
- 新打开但还未完成治理的文档。
- 当前线程中的阶段性判断。
- 临时搜索结果。
- 暂未验证完成的候选知识。
- 当前任务目标摘要。
- 当前 blocker。
- 当前候选 context bundle / 候选 evidence 工作集。

进入条件：
- 当前任务强相关。
- 需要参与当前问答或当前执行。
- 还没完成验证、治理、抽象。
- 未来可能被升格、替换或丢弃。

### 工作记忆层存放位置

工作记忆不应只放进进程缓存，也不应直接落到长期 `memory`。

正式设计应采用：
- 任务/线程作用域持久化工作记忆层。

推荐承载位置：
1. `normalized capture objects`
2. `context bundle / working set`
3. `retrieval working set`
4. `task-scoped structured notes`

也就是说：
- 不是只放缓存。
- 也不是直接变成长记忆。
- 而是放在“可恢复、带 TTL、可参与当前上下文装配的任务级工作记忆层”里。

推荐属性：
- 作用域：`host + thread_id + task_request_id`
- 生命周期：默认短 TTL，可续期
- 状态：`captured / normalized / batched / promoted / discarded / expired`
- 用途：当前任务装配、阶段性引用、必要时作为治理辅助输入

### 当前系统现状

当前系统已经有一些“近似工作记忆层”的对象，但还不完整：
- `captured session / execution trace`
- `memory_candidate`
- `kp_context_bundle`
- 各类 governance preview / batch 结果

这些里只有一部分接近工作记忆层，但仍有三个缺口：
1. 没有统一被定义为“工作记忆层”。
2. 没有统一 TTL / 失效 / 升降级机制。
3. 没有明确与“治理证据层”、长期 `memory`、长期 `knowledge` 的边界。

因此结论是：
- 当前系统不应简单把工作记忆理解为缓存。
- 当前系统也还没有完整工作记忆层。
- 应该把现有部分 context / working set 对象正式收编为 `working memory layer`。

## 4.4 Governance Evidence Layer

定义：
- 只为治理服务、不为日常回答直接服务的治理专用证据层。

这是本轮新增的关键层，用来保存“完整对话记录之外，但治理时必须读取的信息”。

适合进入 `governance evidence layer` 的内容：
- 根据用户需求实际搜索得到的网页、论文、仓库、外部资料摘要。
- 用户上传的知识材料及其清洗/转换结果。
- 会话记录不会完整保留的任务执行步骤。
- 尝试过的路径、失败原因、成功原因、放弃原因。
- 当前执行中的中间判断、候选归纳、待确认冲突项。
- 验证命令、关键输出摘要、工具调用摘要、评测结果摘要。

进入条件：
- 对治理判断有价值。
- 不应直接参与日常问答上下文读取。
- 可能在治理完成后被清理、过期或只保留摘要。

不适合进入这一层的内容：
- 完整对话消息本身
- 当前任务必须频繁读取的工作记忆
- 已确认的长期规则、长期记忆、正式 knowledge

### 治理证据层存放原则

治理证据层应满足：
- 可持久化
- 可按任务/线程/宿主检索
- 可定期清理
- 可供治理批处理读取
- 默认不进入问答上下文装配

推荐属性：
- 作用域：`host + thread_id + task_request_id + project_id`
- 生命周期：比工作记忆更长，但不是永久保留
- 状态：`collected / normalized / consumed / archived / expired`
- 用途：治理输入、治理审计、治理复核

### 执行失败证据要求

治理证据层必须显式保留执行失败与工具不可用信息，而不是只保留“成功路径”。

至少应覆盖：
- 命令失败
- 工具不存在或不可用
- 权限失败
- 路径失败
- 依赖缺失
- 为什么放弃该路径

典型例子：
- 本机 `rg` 不可用
- 某次 `ripgrep`/`rg.exe` 执行被拒绝
- 某个 CLI 未安装

这些内容默认不进入长期 `memory` 或 `knowledge`，但必须进入治理证据层，作为后续治理、复盘和流程修正依据。

### 治理证据层与工作记忆层的区别

工作记忆层：
- 为当前任务问答和执行服务
- 会被上下文装配读取
- 强调当前可用性

治理证据层：
- 只为治理服务
- 日常问答默认不读取
- 强调治理依据与事后复盘价值

因此：
- 不是所有临时信息都进工作记忆层
- 也不是所有中间材料都进原始记录层
- “对当前回答无用，但对治理很重要”的东西，应进入治理证据层

## 4.5 Skill

定义：
- 稳定、可复用的“怎么做”的方法，不是结果，不是事实。

建议分成：
- `active_skill`
- `skill_proposal`

当前阶段默认：
- 系统自动只生成 `skill_proposal`
- 用户确认后才修改真实 `SKILL.md`

适合进入 `skill` 的内容：
- 可复用执行流程。
- 调试与修复套路。
- 何时触发 `interview`。
- 何时做治理、检索、写入。
- 宿主接入与验证流程。

不该进入 `skill` 的内容：
- 一次验证结果。
- 一次接入结论。
- 一次具体命令日志。

## 4.6 Knowledge

定义：
- 外部世界的通用知识。

这是长期知识系统中最严格、最稀缺的一层。

适合进入 `knowledge` 的内容：
- 外部文档、论文、GitHub 项目、产品资料中提炼出的通用知识。
- 多来源归并后的稳定规律。
- 有溯源证据的领域原则、设计模式、方法论。

进入条件，必须同时满足：
1. 来源是外部知识，不是系统内部上下文。
2. 对单个用户、单台机器不特化。
3. 有证据来源。
4. 经过治理、合并、抽象或冲突处理。
5. 不是一次性临时搜索结果。

不该进入 `knowledge` 的内容：
- 本机路径。
- 当前项目治理规则。
- 用户偏好。
- 我们系统自己的内部制度。
- 当前线程临时发现但尚未验证的资料。

结论：
- 系统内部规律：进 `rule` 或 `memory`
- 外部通用规律：进 `knowledge`

## 4.7 Evidence / Source

定义：
- 原始证据层，不直接作为最终长期主层。

包括：
- markdown 原文
- 网页
- 论文
- 命令输出
- MCP 调用记录
- 文件片段

作用：
- 溯源
- 审核
- 复核
- 支撑 `rule / memory / skill proposal / knowledge`

## 4.8 Audit / Execution Trace

定义：
- 执行日志、工具轨迹、运行过程事件。

作用：
- 治理输入
- 失败复盘
- 生成短期层、proposal 和 `knowledge synthesis` 的原料

默认不直接进入长期主层。

## 5. 抽取与升降级流程

统一流程：

1. `capture`
   - 会话
   - 执行记录
   - 外部资料
   - 工具轨迹
   - 文件改动

2. `raw classification`
   - 外部知识
   - 系统内上下文
   - 执行痕迹
   - 临时发现

3. `working / evidence split`
   - 需要参与当前任务装配的，进 `working memory`
   - 只给治理用的，进 `governance evidence layer`
   - 原始底稿保留在 `conversation / execution record layer`

4. `governance routing`
   - 硬约束 -> `rule`
   - 个体化稳定事实 -> `long-term memory`
   - 可复用方法 -> `skill_proposal`
   - 外部通用知识 -> `knowledge`
   - 否则继续留在 `working memory` / `governance evidence layer` 或直接丢弃

5. `promotion / merge / supersede / discard`
   - 去重
   - 合并
   - 抽象
   - 冲突处理
   - 替换旧版本
   - 无价值则删除

## 6. 抽取准则

## 6.1 Rule 抽取准则

必须满足：
- 文本里明确存在长期强约束。
- 能约束未来行为。
- 不是具体事件结果。

抽取方式：
- 优先从用户显式要求中抽。
- 再从已经确认的系统治理边界中抽。
- 自动抽取后必须做去重和归一化。

## 6.2 Long-term Memory 抽取准则

必须满足：
- 与用户、项目、机器、系统高度相关。
- 稳定期足够长。
- 在未来任务中大概率有重复价值。

抽取方式：
- 优先抽用户偏好、环境事实、设计决策、失败经验。
- 不要把一次会话中的全部路径、命令、验证结果直接写成长记忆。

## 6.3 Short-term Memory 抽取准则

必须满足：
- 当前任务强相关。
- 需要参与当前任务上下文装配。
- 还不该直接进入长期层。
- 可能被验证、合并、升格或删除。

抽取方式：
- 对新资料、新搜索结果、新思路先判断是“当前任务工作集”还是“治理证据”。
- 不要因为“看起来有用”就直接写成长记忆或 knowledge。

## 6.4 Governance Evidence 抽取准则

必须满足：
- 对治理判断有帮助。
- 对当前问答不一定直接有帮助。
- 需要在用户显式触发治理、整理或审查时被治理层读取。

抽取方式：
- 对搜索得到的资料、上传知识、执行步骤、失败原因、成功原因、验证依据做结构化保存。
- 默认不进入长期层。
- 默认不直接参与问答读取。
- 由显式触发的治理任务消费、清理、归档；不因每次任务结束自动治理。

## 6.5 Skill Proposal 抽取准则

必须满足：
- 表达的是“怎么做”的稳定方法。
- 至少反映出一个流程级缺口。
- 值得未来复用。

抽取方式：
- 从多次纠偏、重复返工、阶段性理解偏差中归纳。
- 输出为 proposal，而不是直接改 `SKILL.md`。

## 6.6 Knowledge 抽取准则

必须满足：
- 是外部知识。
- 有证据来源。
- 经过治理与抽象。
- 对后续多个任务有通用价值。

抽取方式：
- 默认从外部资料中抽。
- 优先做跨来源合并和冲突处理。
- 避免把“观点列表”误当成治理后的 knowledge。

## 7. 当前方案是否足以支撑目标

结论：
- 当前方案已经足以支撑“正确方向”。
- 但还不足以稳定产出“你真正想要的效果”。

原因：
1. 已经有 host capture、governance batch、proposal、synthesized knowledge 的骨架。
2. 但工作记忆层与治理证据层仍未被正式同时建模。
3. 抽取器仍偏启发式，尚未形成稳定的层级判定能力。
4. `knowledge` 还缺“外部知识限定”和“跨来源合并优先”的强约束。
5. `memory` 和 `knowledge` 的误判仍可能反复出现。

因此判断：
- 框架方向够了。
- 抽取质量控制还不够。

## 8. 需要补强的部分

## 8.1 补正式工作记忆层与治理证据层

必须补：
- `working_memory` 等价层。
- `governance_evidence` 等价层。

最低要求：
- 线程/任务级作用域
- TTL
- 状态机
- promotion / discard / expire 机制
- 工作记忆层与 context assembly 对接
- 治理证据层与 governance batch 对接

## 8.2 补层级判定器

必须补：
- 先判断“外部/内部”
- 再判断“长期/临时”
- 再判断“约束/事实/方法/知识”

这层应成为所有抽取的前置 gate，而不是散落在各个路由里。

## 8.3 补测试集与对照评测

必须补：
- 规则误抽测试
- memory/knowledge 混淆测试
- 短期资料误升格测试
- skill proposal 漏检测试
- 多来源 knowledge 合并测试

没有这些测试，抽取效果会一直漂。

## 8.4 补 Prompt / Method 迭代闭环

必须接受一个现实：
- 用户不会一次性把所有边界讲清楚。

因此系统必须具备：
- 先按当前 spec 抽取
- 输出可审查结果
- 根据用户方向纠偏
- 更新抽取策略
- 必要时触发 `interview`

这和 `interview` skill 的目标是一致的：
- 用户说不全时，系统要能补全。
- 用户只给方向时，系统要能细化。
- 真有关键歧义时，再最小化打断用户确认。

## 9. 本规范对当前实现的直接要求

后续实现应立即执行以下修正：

1. 把新外部资料先判断落到 `working memory` 或 `governance evidence layer`，不得直接入长期 `knowledge`。
2. 把当前 `context / working set` 相关对象正式纳入 `working memory layer`。
3. 把搜索结果、上传知识、执行步骤、失败原因、成功原因、验证摘要等正式纳入 `governance evidence layer`。
4. 为 `knowledge` 增加“仅外部知识可入”的硬 gate。
5. 为 `memory` 增加“仅个体化长期稳定事实可入”的硬 gate。
6. 为 `skill` 保持 proposal-only 策略，未经确认不改真实 `SKILL.md`。
7. 为 `rule` 保持 `must / must_not` 双档策略。
8. 增加抽取质量评测样例，避免每轮修正仍然偏差很大。

## 10. 开工前最终检查清单

在进入下一阶段实现前，必须再次核对以下事项是否已经满足：

1. 会话记录层、工作记忆层、治理证据层三者边界已经明确，不再混用。
2. `knowledge` 只承载外部通用知识的 gate 已作为硬规则执行。
3. `memory` 只承载个体化长期稳定事实的 gate 已作为硬规则执行。
4. `rule` 只允许 `must / must_not` 的策略已锁定。
5. `skill` 仍保持 proposal-only，不会自动修改真实 `SKILL.md`。
6. 治理层默认追求“高价值、低污染”，而不是“多产出”。
7. 新外部资料默认不会直接进入长期层，而是先进工作记忆层或治理证据层。
8. 任务执行步骤、失败原因、成功原因、验证依据会被保存到治理证据层，而不是丢失。
9. 治理验收时能够明确展示：
   - 输入读了什么
   - 丢弃了什么
   - 为什么丢弃
   - 升格了什么
   - 为什么升格
   - 哪些留在治理证据层或工作记忆层
10. 如后续实现中再次出现“理解方向可能偏了、关键边界又开始模糊”，必须重新触发 `interview` 补访谈，而不是继续凭感觉推进。

## 11. 最终结论

工作记忆不是简单缓存。

工作记忆应是：
- 线程/任务作用域的持久化工作记忆层，
- 承载当前任务上下文装配所需的结构化工作集，
- 通过 TTL、状态机和 promotion/discard 机制与长期层衔接。

治理证据层应是：
- 线程/任务作用域的治理专用证据层，
- 承载搜索结果、上传知识、执行步骤、失败原因、成功原因、验证依据等治理材料，
- 默认不参与日常问答读取，
- 只在治理时读取，并定期清理。

长期层则应严格收敛为：
- `rule`：硬约束
- `long-term memory`：个体化长期稳定事实
- `skill_proposal / active_skill`：方法层
- `knowledge`：治理后的外部通用知识

只有先把工作记忆层与治理证据层补齐，把分层 gate 收紧，再配合测试与迭代，系统才可能稳定达到目标效果，而不是每轮都“方向对一点，但结果还差很多”。
