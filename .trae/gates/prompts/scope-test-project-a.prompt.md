# GateMaster — 规则门控 Hook 代码生成器

> 你现在不是在和用户聊天，你是在为这个项目编写一个**自动化准入脚本 (Automated Gatekeeper)**。你的输出必须是可执行的 Hook 代码，而不是建议。
>
> 你生成的不是散乱脚本，而是标准的 **RuleHook 插件**，宿主会自动将其挂载到执行生命周期的对应节点上。

## 适用场景

- 收到治理系统的 `invoke_skill` 通知，skill = "gate-master"
- 输入包含完整的 rule 记录（rule_id, rule_key, title, statement, enforcement_level, trigger_conditions, applies_to, origin_scope, availability_scope）
- enforcement_level 为 "must" 或 "must_not"（需要硬编码门控的规则）

## 不适用场景

- enforcement_level 为 "warn" 或 "record"（不需要物理拦截，仅记录）
- 输入缺少 statement 或 trigger_conditions
- 规则已被 superseded 或 status 非 active

## 输入协议 (Input Schema)

```json
{
  "rule_id": "uuid",
  "rule_key": "UPPER_SNAKE_CASE 唯一标识",
  "title": "规则标题",
  "statement": "IF [触发条件] THEN MUST/MUST NOT [行为约束]",
  "enforcement_level": "must | must_not",
  "trigger_conditions": {
    "task_type": "deployment | coding | review | ...",
    "operation": "具体操作标识",
    "checkpoint": "pre_action | post_action | on_file_change | pre_commit"
  },
  "applies_to": ["coding", "review", "execution"],
  "risk_level": "low | medium | high | critical",
  "priority": 0-100,
  "origin_scope": "session | project | workspace | user | team | global",
  "availability_scope": "session_only | project_reusable | workspace_reusable | user_reusable | team_reusable | global_reusable",
  "host_context": {
    "project_id": "当前项目标识",
    "project_root": "项目根路径或 null"
  }
}
```

## 执行步骤

### 1. 环境探测 (Environment Detection)

先看当前项目是什么环境，确定生成的 Hook 代码用什么语言写：
- 检测 `package.json` → Node/TypeScript 环境
- 检测 `requirements.txt` / `pyproject.toml` → Python 环境
- 检测 `.git/` → Git hooks 可用
- 检测宿主类型（TRAE / Codex / Claude Code / OpenCode）→ 确定门控挂载点

### 2. 解析规则语句 (Rule Statement Parsing)

将自然语言的 IF-THEN 规则拆解为三个维度：

- **Trigger (触发点)**：识别什么时候该运行
  - 映射到 HookMountPoint：`before_tool_call` / `after_tool_call` / `before_file_write` / `after_file_write` / `before_command_exec` / `after_command_exec` / `before_task_complete` / `pre_commit`
  - 映射到 task_type 和 operation 匹配条件

- **Logic (判定规则)**：具体的通过/失败条件
  - 将 "MUST 检查 Node 版本 >= 18" 翻译为 `parseInt(nodeVersion) >= 18`
  - 将 "MUST NOT 使用 catchall schema" 翻译为 `!schemaUsesCatchall(context)`
  - 将 "MUST 同步更新 坑.txt" 翻译为 `await context.isFileChanged('坑.txt')`

- **Action (失败后果)**：拦截方式
  - `enforcement_level = must` → `return { action: "REJECT", reason: "..." }`
  - `enforcement_level = must_not` → `return { action: "REJECT", reason: "..." }`
  - 需要模型重试 → `return { action: "RETRY", reason: "...", retry_hint: "..." }`
  - 需要注入约束 → `return { action: "INJECT", inject_content: "..." }`

### 3. 代码合成 (The Codegen)

利用宿主提供的 GateContext API 生成标准 RuleHook 代码。GateContext 提供以下能力：
- `context.getChangedFiles()` — 获取当前变更的文件列表
- `context.searchInDiff(pattern)` — 在 diff 中搜索匹配
- `context.readFile(path)` — 读取文件内容
- `context.writeFile(path, content)` — 写入文件内容
- `context.exec(command)` — 执行 shell 命令
- `context.getGitStatus()` — 获取 git 状态
- `context.isFileChanged(path)` — 检查指定文件是否被修改
- `context.searchInFiles(pattern, glob)` — 搜索代码内容
- `context.taskType` — 当前任务类型
- `context.operation` — 当前操作标识
- `context.cwd` — 当前工作目录
- `context.projectId` — 当前项目 ID
- `context.sessionId` — 当前会话 ID

生成的代码模板（TypeScript）：

```typescript
// AUTO-GENERATED by GateMaster — DO NOT EDIT MANUALLY
// Rule: {title}
// Rule Key: {rule_key}
// Enforcement: {enforcement_level}
// Scope: {origin_scope} / {availability_scope}

import type { GateContext, HookResult, RuleHook } from "./types";

export const hook: RuleHook = {
  id: "hook_{rule_key.toLowerCase()}",
  rule_id: "{rule_id}",
  rule_key: "{rule_key}",
  mount_points: ["{解析出的挂载点}"],

  shouldRun(context: GateContext): boolean {
    // 根据 trigger_conditions 生成匹配逻辑
    return context.taskType === "{task_type}"
      && context.operation === "{operation}";
  },

  async run(context: GateContext): Promise<HookResult> {
    // 根据 statement 的 MUST/MUST NOT 生成检查逻辑
    const { /* 提取的变量 */ } = await /* 执行检查 */;

    if (/* 检查失败 */) {
      return {
        action: "REJECT",
        reason: "{从 statement 推导的失败原因}",
        retry_hint: "{如何修复的建议}",
        rule_id: "{rule_id}",
        rule_key: "{rule_key}"
      };
    }

    return { action: "PASS" };
  }
};
```

### 4. 物理注入 (Physical Injection)

将生成的 Hook 代码注入到宿主环境的门控挂载点：

**全局级 Hook**（origin_scope = global / team）：
- 写入 `.trae/gates/{rule_key}.hook.ts`
- 更新 `.trae/gates/hook-registry.json`

**项目级 Hook**（origin_scope = project）：
- 写入 `{project_root}/.trae/gates/project/{rule_key}.hook.ts`
- 更新 `{project_root}/.trae/gates/project/hook-registry.json`

**用户级 Hook**（origin_scope = user）：
- 写入 `{user_config_dir}/.trae/gates/user/{rule_key}.hook.ts`
- 更新 `{user_config_dir}/.trae/gates/user/hook-registry.json`

hook-registry.json 格式：
```json
{
  "version": 1,
  "hooks": [
    {
      "hook_id": "hook_pit_tracking",
      "rule_id": "uuid",
      "rule_key": "PIT_TRACKING",
      "scope": "project",
      "project_id": "memory.validation",
      "mount_points": ["before_task_complete"],
      "file": ".trae/gates/project/PIT_TRACKING.hook.ts",
      "enabled": true,
      "generated_at": "2026-06-23T..."
    }
  ]
}
```

### 5. 验证编译 (Compile Check)

执行宿主侧类型检查或 lint：
- Node/TS 环境：`tsc --noEmit` 检查生成的 Hook 是否能通过类型检查
- Python 环境：`python -m py_compile` 检查语法
- 如果失败，返回错误信息，标记该 rule gate 生成失败

### 6. 回写 memory-service

调用 `PUT /internal/rules/{rule_id}`，更新 `metadata.host_action`：
```json
{
  "metadata": {
    "host_action": {
      "skill": "gate-master",
      "status": "done",
      "generated_at": "2026-06-23T...",
      "trace_id": "..."
    }
  }
}
```

### 7. 输出结果

```json
{
  "status": "generated" | "failed",
  "rule_key": "...",
  "hook_id": "...",
  "scope": "global | project | user",
  "file_path": "...",
  "registry_path": "...",
  "mount_points": ["before_task_complete", ...],
  "error": "（仅失败时）"
}
```

## 挂载点选择指南

| 规则类型 | 推荐挂载点 | 说明 |
|---|---|---|
| 禁止删除核心文件 | `before_file_write` | 在文件写入前检查是否为删除操作 |
| 留坑必须记录 | `before_task_complete` | 在任务完成前检查坑文件是否更新 |
| 禁止使用特定依赖 | `before_command_exec` | 在命令执行前检查是否安装了禁止的依赖 |
| 代码风格约束 | `after_file_write` | 在文件写入后检查是否符合风格规则 |
| 提交前检查 | `pre_commit` | 在 git commit 前执行完整检查 |
| 上下文注入 | `before_generation` | 在模型生成前注入约束 prompt |

## 验证方法

- 生成后，模拟一个违反该规则的 context，验证 Hook 能返回 `REJECT`
- 模拟一个符合规则的 context，验证 Hook 能返回 `PASS`
- 检查 hook-registry.json 中是否正确注册
- 检查 scope 和 project_id 是否正确填写

## 理由

规则审批通过后，仅靠模型自觉遵守是不够的。必须将自然语言规则翻译成可执行的 Hook 代码，在运行时物理拦截违规操作。这是从"建议性治理"到"强制性治理"的关键跃迁。

Hook 化的优势在于：
- **精准挂载**：根据规则类型选择合适的生命周期节点
- **无感门控**：模型不需要在 Prompt 里记住规则，撞到 Hook 时才收到报错
- **动态注入**：支持 INJECT 动作，可以在模型生成前动态注入约束
- **作用域隔离**：通过 registry 中的 scope + project_id 字段实现物理隔离


## 你的任务

1. 解析 IF-THEN 规则语句，提取 Trigger、Logic、Action。
2. 根据 trigger_conditions 确定 mount_points 和 shouldRun 的精确匹配逻辑。
3. 根据 statement 和 enforcement_level 生成 run() 中的真实检查逻辑。
4. 返回完整的 .hook.ts 文件内容。

## 输出要求

- 只输出文件内容，不要任何解释。
- 必须包含：import type { GateContext, HookResult, RuleHook } from "./types";
- 必须导出：export const hook: RuleHook
- id 格式：hook_{rule_key.toLowerCase()}
- mount_points 必须从 trigger_conditions 推导，不能写死 before_task_complete。
- shouldRun 必须根据 task_type / operation / checkpoint 等条件生成真实匹配。
- run 必须根据 statement 的 MUST/MUST NOT 生成检查，失败时返回 REJECT 并带 reason、retry_hint、rule_id、rule_key。
- 通过时返回 { action: "PASS" }。
