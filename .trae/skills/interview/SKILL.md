---
name: interview
description: 当用户描述一个新任务、新功能、新页面、新需求，或用户表达不清、边界不清、连续纠偏、明显不满“没有听懂需求”时触发。通过智能访谈确认用户真实意图、挖掘隐含需求、补全用户没说清但会影响结果的关键条件；需要执行时生成结构化 SPEC，并严格按照 SPEC 执行。
---

在开始任何实现之前，必须完成以下流程。这不是建议，是强制要求。

如果用户不是要求实现，而是在讨论、解释、研究、复盘或纠正理解，只要出现“问题边界不清、用户反复纠偏、用户强调先听清楚、用户问题可能有多种解释”的情况，也必须先进入本 skill 的澄清流程。此时目标不是立刻生成 SPEC，而是先把用户真正要问的问题收拢清楚。

## 触发场景

以下任一情况都应触发：

- 用户提出新任务、新功能、新页面、新需求。
- 用户要求“做成文档、整理方案、完整链路、工程化设计、接入方案”等需要先定义边界的工作。
- 用户的问题存在多个合理解释，直接回答容易跑偏。
- 用户连续纠正“不是这个意思”“别管那个”“先停下来”“你没理解我”。
- 用户情绪明显指向“需求没被听懂”，此时必须先复述和确认问题边界。
- 用户指出“这不是常规功能吗”“你怎么一点点补”“你有没有完整想过”“这个入口怎么用”“这个做出来有什么意义”等，说明 agent 只做了局部功能而没有覆盖真实业务闭环。
- 用户提到“后台管理、运维维护、管理端、模型注册、Key 池、路由、套餐、权限、计费、资源维护、工程级、可落地、能演示、压测、安全策略”等系统型关键词时，必须触发本 skill，并进入“资源维护闭环检查”。
- 用户输入里既有明确内容，也有隐含目标，需要帮用户把没说出来的部分挖出来。
- 长讨论、方案评审或设计收敛后，用户用“ok”“可以”“继续”“就这样”“好的”等低信息确认认可当前结论，且下一步会进入脚本、代码、配置、文档、工具或正式产物落地时，必须触发本 skill 的需求执行模式。
- 当用户已经认可当前讨论结论但还没有形成执行清单或 SPEC 时，不要继续补问已确认内容；应先发散整理隐含需求和关键决策点，输出要做什么、为什么做、怎么验收，并生成或更新 SPEC。

不应触发的情况：

- 用户只是要求执行一个明确、低风险、无歧义的单步操作。
- 用户只是问一个事实性问题，且问题对象、范围、输出形式都明确。
- 已有 SPEC 或当前线程已经明确覆盖本次问题边界，且用户没有提出新的分叉。

## 两种工作模式

### 需求执行模式

适用于用户要实现、修改、接入、搭建、生成正式交付物的场景。必须完成访谈、生成或更新 SPEC，再执行。
如果用户已经在前文确认过方案边界，可以不继续提问，但仍必须完成发散性思考、关键决策列表和 SPEC 生成。确认过的结论写入 SPEC 的“决策记录”，未知且会影响返工的点才继续问。

### 意图澄清模式

适用于用户在问概念、链路、设计边界、技术机制，或者正在纠正 agent 理解的场景。此时先不要生成 SPEC，先输出：

- 我理解你现在不是在问什么。
- 我理解你真正要问什么。
- 这个问题的边界是什么。
- 还有哪些隐含点需要确认。
- 如果理解正确，下一步只围绕这个边界回答。

只有当用户确认要形成方案、文档或进入执行，才升级为需求执行模式并生成 SPEC。

## 第一步：理解用户意图

读取用户输入，提取：
- 核心任务是什么
- 涉及的功能类别（auth、payment、dashboard、form 等）
- 当前项目名称（从目录名或配置文件推断）
- 用户明确排除的内容是什么
- 用户真正关注的对象是什么
- 用户没有说清但会影响回答或执行边界的隐含条件是什么

如果处于需求执行模式，输出确认：「已理解任务：[任务描述]，类别：[类别]，项目：[项目名]」。

如果处于意图澄清模式，先输出边界确认：

```text
我先确认你的意思：
- 你不是在问：[排除项]
- 你是在问：[真实问题]
- 当前边界：[只回答/只研究/只设计的范围]
- 需要补齐的隐含点：[1-3 个关键点]
```

在用户边界已经非常明确时，可以直接继续回答；如果边界仍有歧义，必须先问 1-3 个澄清问题。

---

## 第二步：查找已有 SPEC

按以下优先级查找匹配的 SPEC 文件：

1. `SPEC-[项目名]-[类别].md` — 项目级（最优先）
2. `SPEC-[类别].md` — 类别级（通用）

**找到项目级 SPEC：**
- 读取内容
- 对比用户输入，以用户输入为准覆盖冲突部分
- 只针对用户输入中未覆盖的部分做访谈
- 跳到第四步

**找到类别级 SPEC（无项目级）：**
- 读取作为基础参考
- 告知用户：「发现同类 SPEC，将作为基础，针对本项目差异点进行访谈」
- 继续第三步，但只问差异部分

**没有找到任何 SPEC：**
- 继续完整的第三步

---

## 第三步：读取 Memory 和上下文

**必须在生成任何问题之前完成：**

1. 读取平台 memory（CLAUDE.md 或平台对应的 memory 文件）
2. 读取项目配置文件（package.json、requirements.txt、.env、tsconfig.json 等）
3. 扫描现有代码库结构，理解技术栈、已有模式、已有认证方式等

对每一个候选问题，先做推断过滤：

```
能从代码库/配置推断？       → 推断，记录假设，不问
用户 memory 里有记录？      → 沿用偏好，不问
只影响 UI 表现/文案/惯例？   → 自行按惯例处理，不问
答案不影响架构或实现路径？   → 自行决定，不问
```

只有**无法推断且影响架构或实现路径**的问题，才进入第四步。

---

## 第四步：发散性思维，生成候选问题

对用户任务从以下维度发散，找出潜在的关键决策点：

**功能边界**
- 这个功能做到哪，明确不做什么
- 与现有功能的边界和关系

**异常与边界情况**（只问影响架构的）
- 失败/错误处理方式是否影响流程设计
- 边界情况的处理是否影响数据结构

**体验细节**（只问影响实现方案的）
- 移动端适配要求
- 加载策略（懒加载/预加载/骨架屏）

**安全与性能**
- 数据敏感级别（影响存储和传输方案）
- 并发量级/响应时间要求（影响架构选型）
- 认证和权限模型

**数据层面**
- 数据是否需要持久化
- 数据归属和隔离方式（个人/团队/全局）

**与现有系统的关系**
- 影响哪些已有模块
- 是否需要兼容旧数据或旧接口

**资源维护闭环（后台/运维/管理端任务必跑）**
当任务涉及任何“可配置资源”时，例如用户、租户、应用、套餐、平台 SK、真实上游 SK、Key 池、模型、厂商、路由、计费规则、参数模板、权限策略，必须逐一检查以下动作是否需要实现或明确不做：
- 新增/导入：资源从哪里来，谁创建，是否支持批量或导入真实凭据
- 查看/列表/详情：列表展示什么，详情隐藏什么，敏感字段如何脱敏
- 编辑：哪些字段可改，哪些字段不可改，改动后何时生效
- 启用/停用/吊销/归档：状态机是什么，是否影响线上请求
- 删除：物理删除还是软删除，是否保留审计和历史账单
- 绑定关系：资源和哪些对象关联，例如 SK -> 套餐策略 -> 模型范围 -> 路由 -> Key 池 -> 真实上游 SK
- 测试验证：配置后如何证明可用，例如连通性测试、模拟调用、配置校验
- 容量与并发：单资源容量、池化分发、限流、满载时行为
- 防重复与一致性：重复导入、重复绑定、孤儿资源、无效引用如何处理
- 审计与回滚：谁改了什么，是否需要操作日志、版本、回滚或影响分析
- 错误反馈：失败时前端/接口返回什么，用户能否定位配置错误

如果任一项无法从上下文推断，必须写入 SPEC 的“待确认/本期不做/后续风险”，不能静默跳过。

**真实链路反推（网关、接入、平台型系统必跑）**
不能只从页面字段或接口字段正向设计，必须从真实使用者动作倒推完整链路：
- 客户/调用方拿到什么？不能看到什么？
- 运维/管理员如何把后端资源接进系统？
- 请求进来后依次经过哪些鉴权、策略、路由、容量、计费、转发、回写步骤？
- 如果某个配置对象存在，它的业务目的是什么？为了达成目的还缺哪些入口？
- 如果只有一个资源实例，例如一个真实上游 SK，会不会被多个调用方打爆？池化、限流、降级怎么处理？
- 如果配置错误或上游不可用，系统怎么暴露错误、保护成本、避免泄露敏感信息？

**扩展性**
- 这个功能以后最可能往哪个方向扩展
- 现在的设计边界是否需要为此预留空间

**用户大概率没想到的隐含问题**
- 深挖用户输入背后的假设
- 找出容易在后期引发返工的决策点
- 不问显而易见的问题，只挖用户可能忽略的硬问题

对所有候选问题再过一遍过滤条件，只保留真正需要问的。
如果用户已经明确认可当前讨论结论，则本步骤不一定要继续提问，但必须产出“隐含需求 / 关键决策 / 执行清单”。其中已经能从对话推断或用户已确认的内容直接写入 SPEC；只有会影响架构、数据边界、验收或返工风险且无法从上下文推断的点，才进入下一步提问。

---

## 第五步：决策树式提问

**不要一次列出所有问题。**

按决策树顺序提问：
- 先问根节点问题（答案会影响后续问题范围的）
- 根据答案动态决定下一个问题
- 答案已经排除的分支，对应问题直接跳过

每次只问 1-3 个问题，等用户回答后再继续。

问题要求：
- 不问显而易见的问题
- 不问用户肯定会说"是"的问题
- 每个问题都给出 2-4 个具体选项（含简短说明）
- 选项之间要有真实的架构或实现差异
- 如有推荐选项，标注「（推荐）」并说明原因

持续访谈直到所有关键决策点都已覆盖。

---

## 第六步：生成 SPEC 文件

访谈完成后，生成 `SPEC-[项目名]-[类别].md`：

```markdown
# [功能名称]

## 目标
一句话说清楚要做什么、为谁做、解决什么问题。

## 决策记录
列出所有关键决策，注明来源：
- [决策项]：[结论]（来源：用户指定 / memory 沿用 / 代码库推断 / 访谈确认）

## 假设
列出所有自行推断或按惯例处理的内容：
- 假设 [X]，原因：[推断依据]
- 按惯例处理 [Y]，后期可调整

## 实现范围
### 做
- [具体要实现的内容]

### 不做（本期）
- [明确排除的内容]

## 资源维护闭环
- [涉及的资源 1]：新增/导入、查看、编辑、状态、删除/归档、绑定关系、测试验证、容量/限流、审计/错误反馈分别如何处理。
- [涉及的资源 2]：同上。

## 链路反推
- 使用者入口：[客户/管理员/运维分别从哪里进入]
- 主链路：[请求或配置从入口到最终生效的步骤]
- 关键保护：[鉴权、权限、敏感信息、并发、限流、失败保护]

## 验收标准
- [可验证的完成条件]
- 后台/运维类功能必须能完成真实维护动作，而不是只有列表或启停；每个资源至少验证“创建/导入 -> 生效/绑定 -> 调用或测试 -> 状态变更/错误处理”。
- 涉及密钥、token、凭据、内网地址的功能必须验证“不在客户侧、日志、普通列表响应中泄露明文”。

## 用户偏好记录（本次新增）
- [本次访谈中发现的可复用偏好，含否决类]
```

生成后，输出：「SPEC 已生成，请确认假设部分是否有偏差，确认后开始执行。」

等待用户确认或修正。

---

## 第七步：严格按 SPEC 执行

**执行过程中：**
- 每个实现决策必须能对应到 SPEC 中的某一条
- 遇到 SPEC 未覆盖的分叉点，必须停下来，补充访谈，更新 SPEC，再继续
- 不能自己假设 SPEC 没写到的内容，必须问
- 对后台/运维/平台型系统，不能只实现字段、列表或启停按钮；必须按 SPEC 中的“资源维护闭环”和“链路反推”逐项自检。
- 如果实现过程中发现某个资源存在但缺少创建/导入、绑定、生效、测试、容量、安全或错误反馈入口，必须先补 SPEC，再继续实现。

**不允许：**
- 在 SPEC 之外自行做架构决策
- 忽略 SPEC 中的否决类偏好
- 跳过 SPEC 中明确列出的验收标准
- 把“看得到资源”当成“能维护资源”，把“能保存字段”当成“链路可用”，把“接口返回成功”当成“业务闭环完成”。

## 第七步附加门禁：常规功能完整性自检

在交付后台、网关、平台、计费、权限、资源管理、接入系统前，必须回答并验证：

- 运维能否从空配置开始完成接入？
- 客户能否只用允许暴露的信息完成调用？
- 敏感信息是否全程不回显、不进普通日志、不出现在客户侧？
- 多个调用方打同一资源时是否有池化、限流或明确拒绝策略？
- 配错、重复、过期、停用、余额不足、上游失败时是否有可定位的错误？
- 管理端页面、Admin API、Gateway 实际链路是否使用同一套配置来源？
- 测试是否覆盖正向、拒绝、敏感信息不泄露和至少一个真实/模拟链路？

自检不通过时，不允许报告“完成”，只能报告剩余缺口和下一步修复。

---

## 第八步：完成后写回 Memory 和维护类别级 SPEC

**任务完成后，这一步是强制的，不可跳过。**

**写回 memory：**
提炼本次对话中用户表达的偏好，包括：
- 正向偏好：用户倾向用什么、怎么做
- 否决偏好：用户明确拒绝的方案或风格

格式：
```
- [偏好描述，一句话，含正向或否决标记]
```

已有条目不重复，有冲突的更新为最新表达，写入平台 memory 文件的 `User Preferences` 部分。

**维护类别级 SPEC：**
分析本次项目级 SPEC，提炼与项目无关的通用决策，更新或创建 `SPEC-[类别].md`。

如果发现与其他项目同类 SPEC 存在明显差异（如认证方式完全不同），主动告知用户：
「发现你在不同项目中对 [类别] 有不同处理方式，是否将其中一种设为默认偏好？」

---

## 全局原则

- 用户输入永远优先于 SPEC，SPEC 优先于 memory
- 问题质量比问题数量重要，宁可少问，不问废话
- 所有假设必须透明，写入 SPEC 的假设部分
- 否决类偏好和正向偏好同等重要，都必须记录和遵守
- 每个强制步骤完成后输出一句确认，让用户知道执行进度
